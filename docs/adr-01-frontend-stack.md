# Решение 01. Интерфейс: TypeScript или HTML

## 1 Вопрос поставлен неточно

«TypeScript или HTML» — это выбор языка. Но в проекте, который **скачивают и
разворачивают у себя**, решает не язык, а другое: что после этого выбора должно
оказаться установленным на машине пользователя.

Ответ на этот вопрос и определяет всё остальное. Поэтому дальше сравниваются не
языки, а способы доставки интерфейса.

## 2 Что делали раньше

| Проект | Интерфейс | Как попадает к пользователю |
|---|---|---|
| RAGRAF | React 18 + TS + Vite + Tailwind, TanStack Query, Zustand, cytoscape, reactflow | **собирается на машине пользователя**: `npm install` + `npm run build` |
| GONKA | React + Vite + Zustand + i18next, PWA | деплой, пользователь получает готовую сборку |
| KNIFFEL | Vite + TS | то же |
| demo-sigma | React 19 + Vite 8 | то же |
| SOFIA | Expo / React Native + TS | то же |
| AI-SKLAD | статический HTML без сборки | демо-рассылка, категория D |
| STROY | Streamlit (интерфейс генерирует Python) | демо |

ADR-001 фиксирует дефолт: React 18 + TS strict + Vite + Tailwind + TanStack Query
+ Zustand. Шесть проектов из семи ему следуют. Исключение одно — AI-SKLAD, и это
демо на рассылку, где интерфейс вторичен.

Два факта, которые я проверил, а не взял из памяти:

- `frontend/dist` у RAGRAF весит 46 МБ, но JavaScript и CSS в нём — **2,5 МБ**.
  Остальное — видео на 35 МБ и скриншоты. То есть «React тяжёлый» — неверный
  аргумент: 2,5 МБ приходятся на приложение с cytoscape, reactflow, dnd-kit и
  роутером, а наше сильно проще.
- `dist` у RAGRAF **не лежит в git** — он в `.gitignore`. Именно поэтому лаунчер
  вынужден собирать фронтенд на машине пользователя.

## 3 Чем этот проект отличается от всех предыдущих

Три отличия, и каждое давит на решение.

**Инструмент разворачивает пользователь, а не вы.** Во всех прошлых проектах
сборку делали вы, а человек получал готовое: открыл ссылку — работает. Здесь он
скачивает репозиторий и запускает у себя. Всё, что нужно собрать, придётся
собирать ему.

**Этот пользователь — сотрудник вуза на Windows.** Не разработчик. Node.js,
`npm install` и пятиминутная сборка — три дополнительные точки отказа на пути,
где он и так может сорваться. Напомню замеры из плана: цепочка установки под
Windows — пять шагов, и вероятнее всего человек срывается на четвёртом (окно
SmartScreen) и пятом (решает, что зависло).

**Требование автономности.** §8.2 обещает, что данные не уходят наружу. Значит
никаких CDN: ни `unpkg`, ни `jsdelivr`, ни шрифтов Google. Всё, что нужно
странице, лежит рядом с ней. Это, кстати, снимает и вопрос корпоративных сетей,
которые CDN блокируют.

Вывод: **повторять схему RAGRAF нельзя.** Не потому, что она плохая — для
RAGRAF она разумна, там аналитик заказчика и так ставит git с python, — а потому
что здесь она добавила бы Node.js в список обязательного и превратила бы запуск
в пятиминутную сборку с непредсказуемым исходом.

## 4 Критерий выбора

Что должно оказаться на машине пользователя, чтобы интерфейс открылся:

| Вариант | Нужен Node | Нужна сборка у пользователя | Кто собирает |
|---|---|---|---|
| А. HTML + vanilla JS без сборки | нет | нет | никто, файлы отдаются как есть |
| Б. React + TS + Vite, сборка в CI | нет | нет | GitHub Actions, готовый `dist` едет в пакет |
| В. Как RAGRAF: сборка у пользователя | **да** | **да, 2–5 минут** | пользователь |

Вариант В отпадает сразу — см. раздел 3. Реальный выбор между А и Б, и он
сводится к одному вопросу: **выдержит ли редактор отсутствие сборщика.**

## 5 Решающий аргумент — редактор

Здесь решает не вкус, а упаковка библиотек. Проверено сегодня через npm:

| Пакет | Версия | Что отдаёт |
|---|---|---|
| `codemirror` | 6.0.2 | `dist/index.cjs` (CommonJS) и `dist/index.js` (ESM) — **браузерной сборки нет** |
| `markdown-it` | 15.0.1 | CJS и ESM |
| `github-markdown-css` | 5.9.0 | обычный CSS, 170 КБ |

CodeMirror 6 — это не одна библиотека, а десяток пакетов (`@codemirror/state`,
`@codemirror/view`, `@codemirror/lang-markdown` и так далее), связанных импортами.
Готового файла, который подключается через `<script>`, у него нет вообще. Без
сборщика его придётся разрешать вручную через import maps, перечисляя все
транзитивные зависимости — и чинить это при каждом обновлении.

Оформление и разметка при этом никакой сборки не требуют: `github-markdown-css` —
просто файл, `markdown-it` подключается одним модулем.

Значит вопрос сужается ещё раз: **редактор либо примитивный `<textarea>`, либо
сборщик.**

`<textarea>` — это отказ от подсветки синтаксиса, от подсветки ошибок валидатора
прямо в тексте и от нумерации строк. А подсветка ошибок в тексте — половина
смысла этапа 4: без неё диагностика возвращается в отдельный список, и мы
приходим к тому же, что было в Tkinter, только в браузере.

## 6 Решение

**React 18 + TypeScript strict + Vite + Tailwind. Сборка выполняется в CI и
никогда — на машине пользователя.**

Это ADR-001 с одним жёстким дополнением, которое и делает выбор безопасным:
собранный `dist` кладётся внутрь Python-пакета, а Node.js остаётся инструментом
разработчика и CI. Пользователь про него не знает.

Почему не вариант А, если он проще:

- CodeMirror без сборщика не подключается (раздел 5);
- вы работаете соло с LLM, а LLM пишет React и Tailwind заметно лучше, чем
  ручные операции с DOM — на объёме в 10–15 экранных элементов это разница в
  днях;
- шесть проектов из семи уже на этом стеке, и всё, что вы про него знаете,
  переносится;
- аргумент «React тяжёлый» опровергнут замером: 2,5 МБ у RAGRAF со всей его
  графовой машинерией.

Почему не вариант В — раздел 3.

### Отклонения от ADR-001, сделанные сознательно

| Компонент ADR-001 | Здесь | Почему |
|---|---|---|
| TanStack Query | **не берём** | серверного состояния нет: одна операция сборки и одна проверка. Кэш и инвалидация решают задачу, которой у нас не существует |
| Zustand | берём, но минимально | состояние редактора и настроек профиля; для двух панелей хватит одного стора |
| React Router | не берём | экранов два, роутинг не нужен |

Остальное по ADR-001 без изменений. Новый ADR в vault для этого не нужен — это
не смена стека, а его усечение под задачу.

### Состав фронтенда

| Библиотека | Версия | Назначение |
|---|---|---|
| React + TypeScript strict | 18.3 / 5.6 | ADR-001 |
| Vite | 5.4+ | сборка, HMR при разработке |
| Tailwind | 3.4 | оформление |
| CodeMirror | 6.0.2 | редактор: подсветка Markdown, диагностики в тексте |
| markdown-it | 15.0.1 | предпросмотр |
| github-markdown-css | 5.9.0 | вид «как на GitHub» |

Всё это ставится локально и попадает в бандл. Ни одной ссылки на CDN.

## 7 Что из этого следует для доставки

Одно неочевидное последствие, которое надо учесть сразу, иначе оно всплывёт на
этапе 5 и сломает установку.

`dist` не коммитится в git — как и в RAGRAF, это генерируемый артефакт. Но тогда
команда `uv tool install git+https://github.com/…` соберёт пакет **из исходников
без готового фронтенда**, и интерфейс не откроется.

Поэтому установка идёт не из git, а из собранного пакета:

| Способ | Команда | Когда |
|---|---|---|
| Основной | `uv tool install md2gostdocx` | если пакет опубликован на PyPI |
| Без PyPI | `uv tool install <ссылка на .whl из GitHub Releases>` | колесо собирает CI и прикладывает к релизу |
| Офлайн | архив релиза с колесом внутри | заблокированная сеть, машина без интернета |

И связанная с этим ловушка, проверенная в исследовании: если в `.gitignore`
появится `*.docx` (а он появится — в плане есть pre-commit-хук, запрещающий
коммитить сгенерированные DOCX), то `hatchling` молча не положит в колесо
`reference.docx`. Симптом коварный: инструмент работает, профили показываются, а
DOCX собирается без ГОСТ-стилей.

Страховка одна и она уже заложена в раздел 12 плана: после установки собрать
пробный DOCX установленным бинарём и проверить, что в `styles.xml` есть Times New
Roman. Проверять надо и наличие `dist` — тем же способом, обращением к
собственному интерфейсу.

## 9 Что не проверено

Исследование по редактору не было завершено, и это решение опирается только на
упаковку библиотек, а не на опыт их совместной работы. Не проверено:

- как CodeMirror 6 ведёт себя с кириллицей и с системами ввода;
- насколько точно `markdown-it` совпадает с рендерером GitHub — известно, что
  расхождения есть, но их список не составлен;
- сколько весит итоговый бандл именно с этим набором;
- синхронная прокрутка двух панелей — насколько она дорога.

Ни один из этих пунктов не отменяет решения: они влияют на трудоёмкость этапа 4,
а не на выбор между сборщиком и его отсутствием. Но перед началом этапа 4 их
стоит закрыть — иначе оценка в 5–7 дней держится на честном слове.
